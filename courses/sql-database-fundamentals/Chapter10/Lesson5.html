Chapter 10 · Changing Data Safely

Safe Change Workflows with Transactions and Verification

Production-safe SQL is a workflow, not a single statement: define the target, lock the scope, change the data, verify invariants, record evidence, and commit only when every check passes.

Beginner120–145 minutesTransactional change runbookLast reviewed: August 2026
On this page

    Learning outcomes

    A safe data change is an auditable decision process. Transactions provide atomicity, but the operator must still define expected rows, verify business invariants, handle retries, and preserve evidence.

    01

    Convert a business change into a preflight query and explicit assertions.

    02

    Use BEGIN, SAVEPOINT, ROLLBACK, and COMMIT deliberately.

    03

    Verify affected rows with RETURNING, changes(), and reconciliation queries.

    04

    Build idempotency and audit evidence into repeatable operations.

    05

    Write a production change runbook with a tested rollback path.

    The governed change loop

    Define scope and owner
    Back up or establish recovery point
    Preflight SELECT and count
    BEGIN write transaction
    Apply change
    Verify rows and invariants
    Record evidence
    COMMIT or ROLLBACK

    A transaction protects atomicity; the surrounding runbook protects intent, observability, and recovery.

    Step 1: turn assumptions into queries

    sqlite · preflight contract
    SELECT    order_id,    external_ref,    status,    total_amountFROM sales_orderWHERE order_id = 101  AND status = 'draft'  AND total_amount = 0;SELECT COUNT(*) AS expected_rowsFROM sales_orderWHERE order_id = 101  AND status = 'draft'  AND total_amount = 0;

    Record the expected count and representative values before the change. If the live result differs, stop and investigate instead of adapting the mutation casually.

    Step 2: open an intentional transaction

    sqlite · acquire the write transaction early
    BEGIN IMMEDIATE;UPDATE sales_orderSET    status = 'paid',    total_amount = 69.00WHERE order_id = 101  AND status = 'draft'  AND total_amount = 0RETURNING order_id, external_ref, status, total_amount;

    BEGIN IMMEDIATE asks SQLite for a write transaction at the start, so lock contention is discovered before the operator performs a long sequence of checks and changes.

    Step 3: use savepoints for recoverable substeps

    sqlite · isolate a risky substep
    SAVEPOINT adjust_inventory;UPDATE productSET stock_qty = stock_qty - 1,    updated_at = CURRENT_TIMESTAMPWHERE sku = 'SQL-QUERY'  AND stock_qty >= 1;SELECT changes() AS inventory_rows_changed;-- If verification fails:ROLLBACK TO adjust_inventory;RELEASE adjust_inventory;-- If verification succeeds, just release it:-- RELEASE adjust_inventory;

    A savepoint does not replace the outer transaction. It creates a named rollback boundary within it.

    Step 4: verify row counts and invariants

    sqlite · post-change assertions
    SELECT changes() AS rows_changed;SELECT    order_id,    status,    total_amountFROM sales_orderWHERE order_id = 101;SELECT COUNT(*) AS invalid_ordersFROM sales_orderWHERE total_amount < 0   OR status NOT IN ('draft', 'paid', 'cancelled', 'refunded');PRAGMA foreign_key_check;

    changes() reports the most recent top-level DML change count for the connection. Business assertions and foreign-key checks test properties that a row count alone cannot prove.

    Step 5: make retries recognizable

    sqlite · request ledger before applying once
    INSERT INTO change_request (    request_key,    operation)VALUES (    'order-101-mark-paid-v1',    'Mark WEB-101 paid at 69.00')ON CONFLICT (request_key) DO NOTHING;SELECT changes() AS request_claimed;

    Continue with the mutation only when the request ledger reports one inserted row. A retry that reports zero is already claimed or applied and must be reconciled rather than repeated blindly.

    Complete guarded workflow

    sqlite · one auditable unit
    BEGIN IMMEDIATE;INSERT INTO change_request (request_key, operation)VALUES ('order-101-mark-paid-v1', 'Mark WEB-101 paid at 69.00')ON CONFLICT (request_key) DO NOTHING;-- The application must assert that the prior statement inserted one row.UPDATE sales_orderSET    status = 'paid',    total_amount = 69.00WHERE order_id = 101  AND status = 'draft'  AND total_amount = 0RETURNING order_id, status, total_amount;-- Assert one returned row and all post-change invariants.COMMIT;
    SQL alone is not the whole control plane

    Some assertions must be enforced by application code, a migration framework, a stored procedure, or an operator runbook. A COMMIT should be conditional on those checks succeeding.

    Change evidence record

    FieldEvidence
    Change IDStable ticket, migration, or request key.
    Owner and approverWho executed and who authorized the change.
    Target definitionExact SELECT, predicate, and expected count.
    Recovery pointBackup, snapshot, replica, or reversible script.
    MutationVersion-controlled SQL and parameter values.
    VerificationRETURNING rows, counts, invariants, and sampled results.
    OutcomeCommit or rollback time, plus incident notes if applicable.

    Operational safety checklist

    Scope

    Bounded target

    Prefer keys, explicit time windows, and expected old state.

    Atomic

    Transaction

    Keep dependent writes and verification in one decision boundary.

    Retry

    Idempotency

    Use stable unique request keys or naturally idempotent predicates.

    Recover

    Rollback

    Test recovery before executing the change, not after failure.

    Capstone practice

    Prepare a runbook that marks order 101 paid, decrements one unit of SQL-QUERY inventory, records a request key, verifies all counts, and rolls back on any mismatch.

    sqlite · capstone transaction skeleton
    BEGIN IMMEDIATE;INSERT INTO change_request (request_key, operation)VALUES ('capstone-order-101-v1', 'Pay order 101 and reserve inventory')ON CONFLICT (request_key) DO NOTHING;UPDATE sales_orderSET status = 'paid', total_amount = 69.00WHERE order_id = 101  AND status = 'draft'  AND total_amount = 0;UPDATE productSET stock_qty = stock_qty - 1,    updated_at = CURRENT_TIMESTAMPWHERE sku = 'SQL-QUERY'  AND stock_qty >= 1;SELECT order_id, status, total_amountFROM sales_orderWHERE order_id = 101;SELECT sku, stock_qtyFROM productWHERE sku = 'SQL-QUERY';PRAGMA foreign_key_check;-- COMMIT only after the application verifies every expected count.ROLLBACK;

    Checkpoint

    Approve or roll back

    1. What does a transaction guarantee, and what does it not prove?
    2. Why acquire a write transaction before a long change workflow?
    3. What is the purpose of a savepoint?
    4. Why are row counts insufficient by themselves?
    5. What makes a change safely retryable?
    Review the answers

    A transaction supplies atomicity and isolation rules but does not prove business intent. Early lock acquisition exposes contention. Savepoints create internal rollback boundaries. Invariants and sampled values complement counts. Stable unique request identity or naturally idempotent predicates make retries recognizable.

    Chapter 10 summary

    • INSERT, UPDATE, and DELETE are set-based operations governed by constraints and predicates.
    • Upsert behavior must be tied to an enforced unique identity.
    • Retention, archival, and soft deletion are data-lifecycle choices.
    • Transactions, assertions, evidence, and recovery plans form the safe-change workflow.
